# Как устроен «Браузер агента»

Документ для тех, кто будет поддерживать плагин или захочет повторить схему.
Здесь — почему сделано именно так, какие места самые хрупкие и что проверять
при изменениях.

---

## 1. Задача

Нужен браузер, который:

1. **видит человек** — иначе капчу и 2FA не решить;
2. **свой у каждого чата** — два агента в разных чатах не должны мешать друг
   другу и не должны делить cookie;
3. **управляется агентом** через обычные инструменты DSH;
4. **ставится без зависимостей** — Electron уже несёт Chromium.

Первые три пункта исключают headless-MCP: там браузер живёт вне интерфейса и
не может ни показать себя, ни пустить человека в цикл.

---

## 2. Три части и один мост

```
┌──────────────────────────── DSH ────────────────────────────┐
│                                                             │
│  Хост (Node, главный процесс)      Клиент (Chromium, окно)   │
│  ┌────────────────────┐             ┌─────────────────────┐  │
│  │ lib/index.js       │             │ lib/client.js       │  │
│  │                    │             │                     │  │
│  │ 22 инструмента     │             │ панель <webview>    │  │
│  │ настройки, журнал  │             │ сторож открытия     │  │
│  └─────────┬──────────┘             └──────────┬──────────┘  │
│            │ HTTP                              │ HTTP        │
│            └──────────► lib/bridge.mjs ◄───────┘             │
│                        маршрутизация по сессии              │
│                              │                               │
│                    ┌─────────┴──────────┐                    │
│                    │ webview сессии A   │  профиль A         │
│                    │ webview сессии B   │  профиль B         │
│                    └────────────────────┘                    │
└─────────────────────────────────────────────────────────────┘
```

Почему мост, а не прямой вызов: инструмент исполняется в хосте (Node), а
браузер живёт в окне (Chromium). Это разные процессы, общего объекта между
ними нет. Мост — тонкий маршрутизатор: список панелей, их сессии и передача
команд длинным опросом.

---

## 3. Маршрутизация: как команда находит свой браузер

Это главная часть, ради которой всё переделано.

### 3.1. Ключ — сессия агента

У каждого вызова инструмента есть `exec.agent.id` — идентификатор сессии, в
которой работает агент. Хост передаёт его мосту:

```js
// lib/index.js
function sessionOf(exec) {
  const id = exec && exec.agent && exec.agent.id
  return id === undefined || id === null ? undefined : String(id)
}
```

Мост выбирает панель **этой** сессии:

```js
// lib/bridge.mjs
function pickPanel(sessionId, hints) {
  const candidates = panelsOf(sessionId)   // только панели этой сессии
  return candidates[0]                     // видимая, затем самая свежая
}
```

Отсюда следует: два агента в разных чатах не могут перехватить команды друг
друга, даже если работают одновременно. Раньше выбор был «самая недавно
активная вкладка» — и именно это давало баг «браузер открылся не в том чате».

### 3.2. Откуда панель знает свою сессию

Узел панели лежит внутри поддерева сессии, и DSH помечает его атрибутом:

```js
// lib/client.js
function sessionFromDom(element) {
  const node = element.closest('[data-sidebar-right-session]')
  return node ? node.getAttribute('data-sidebar-right-session') : ''
}
```

Это надёжнее, чем искать сессию через сервисы: атрибут уже на месте к моменту
монтирования и не зависит от того, какой сервис доступен.

### 3.3. Открытие вкладки в нужной сессии

Вкладку можно создать только в сессии, чей store правой панели уже создан, а
создаётся он при показе чата. Поэтому сторож открытия при необходимости
переключает чат:

```js
// lib/client.js — упрощённо
async function withSession(sessionId, focus, action) {
  const previous = onScreen()
  const switched = previous !== sessionId
  if (switched) {
    switcher.openSession(sessionId)
    await waitFor(() => onScreen() === sessionId, 4000)
  }
  try {
    return await action()          // openTab / focus / close
  } finally {
    if (switched && !focus) switcher.openSession(previous)  // вернуть прежний чат
  }
}
```

`focusOnOpen` управляет тем, останется ли чат переключённым. По умолчанию
остаётся: человек должен видеть, что делает агент.

### 3.4. Несколько окон DSH

Мост общий на процесс, а окно может быть не одно. Поэтому управляющая команда
уходит **всем** подключённым страницам сразу: сессия известна только клиенту,
поэтому отвечает та страница, у которой она есть, а остальные отвечают
`not-mine`, и это не ошибка.

```js
// lib/bridge.mjs
for (const target of targets) deliver(target.inbox, { ...command, id })
// первый ok побеждает; not-mine уменьшает счётчик ожидающих
```

## 4. Изоляция профилей

`window.dshDesktop.browser.acquire(workspace)` возвращает `{ lease, partition }`.
`partition` — это отдельная сессия Chromium. Ключевое свойство: **один и тот же
`workspace` даёт один и тот же `partition`**, разные — разные.

Плагин берёт ключ с идентификатором сессии:

```js
const workspace = 'dsh-agent-browser:' + sessionId
const lease = await window.dshDesktop.browser.acquire(workspace)
```

Следствия:

- каждый чат получает свой Chromium-профиль: cookie, localStorage, логины;
- агент не видит личные cookie пользователя из его повседневного браузера;
- профили живут в памяти процесса, поэтому после перезапуска DSH логины
  теряются. Это осознанный компромисс: изоляция важнее сохранности.

Если понадобится постоянный профиль, менять надо здесь — и тогда стоит
подумать о шифровании и о том, что агент получает доступ к сохранённым сессиям.

## 5. Транспорт

### 5.1. Основной путь: маршрут на встроенном веб-сервере

```js
ctx.webServer.register({ kind: 'prefix', path: '/dsh-agent-browser', handler })
```

Почему так лучше отдельного порта:

- тот же origin, что у страницы → нет CORS и preflight;
- нет фиксированного порта → два окна DSH не конфликтуют;
- нет «потерянного» слушателя после HMR;
- клиенту не нужно узнавать адрес.

Сервис читается через `ctx.reflect.get('webServer')`, а не через `inject`:
`inject` в Cordis только обязательный, и объяви мы `webServer` там — плагин бы
не загрузился в профиле без веб-сервера. А нам нужен резервный путь.

### 5.2. Резервный путь: собственный сервер

Если встроенного сервера нет (окно на `file://`), поднимается сервер на
`127.0.0.1` со случайным портом. Клиент узнаёт адрес и токен из `index.html`:

```js
webServer.tapIndex(html => html.replace('</head>', `<script>window.__DSH_AGENT_BROWSER__=…</script></head>`))
```

### 5.3. Почему длинный опрос, а не WebSocket

Длинный опрос (25 с) проще: нет рукопожатия, нет переподключения, нет
состояния соединения — только HTTP. Для команд «нажми и верни результат» этого
достаточно. Таймауты выстроены по возрастанию, чтобы ошибка приходила с
понятным текстом, а не обрывом:

```
опрос панели 25 с  <  команда 30 с  <  запрос инструмента 45 с
```

## 6. Самое хрупкое

| Место | Что ломается | Как проверять |
|---|---|---|
| `sessionFromDom` | атрибут переименуют → панель не найдёт сессию | в журнале нет `панель подключилась` |
| `withSession` | store сессии не создаётся → `openTab` бросает | тест на открытие в неактивном чате |
| `pickPanel` | несколько панелей → не та получает команды | `browser_tabs` и подпись чата в панели |
| HMR | второй `listen` / потерянная панель | проверка «мост уже поднят» и `globalThis` |
| `page-title-updated` | заголовок не обновляется | визуально в чипе вкладки |
| `dom-ready` | стелс не применился к новой странице | `navigator.userAgent` через `browser_eval` |

## 7. Что проверяют тесты

`test/bridge.test.mjs` (19 тестов, без сети и без DSH) покрывает именно
маршрутизацию и защиту — то, что нельзя проверить глазами:

- команда уходит панели **своей** сессии, а не соседней;
- без панели — внятный код `no-panel`, а не молчание;
- из двух панелей одной сессии выбирается видимая;
- точный `panel` перебивает выбор по сессии;
- ошибка панели превращается в отказ с текстом;
- управляющая команда доходит до страницы и возвращает результат;
- одно окно отвечает `not-mine`, второе берёт команду;
- без токена — 403, токен не утекает в ответ;
- CORS не звёздочка;
- тело больше 8 МБ — 413;
- длинный опрос не подвешивает запрос.

Чего тесты **не** покрывают и что проверяется только руками: сам `<webview>`,
аренда профиля, переключение чатов, нативные события мыши.

## 8. Как расширять

Новый инструмент — это запись в массиве, который возвращает `createTools()`:

```js
{
  name: 'browser_my_action',
  description: 'Что делает — так, чтобы модель поняла, когда звать.',
  parameters: { arg: { type: 'string', required: true, description: 'Смысл' } },
  run: async (args, exec) => {
    const result = await call({ type: 'myAction', arg: args.arg }, exec)
    return 'Что увидит модель'
  },
}
```

На стороне клиента — ветка в `runCmd()`:

```js
if (cmd.type === 'myAction') {
  return { value: await evalJs(...) }
}
```

Правила, которые лучше не нарушать:

1. **Никогда не выбирать панель «по свежести»** — только по сессии.
2. **Таймауты по возрастанию**: опрос < команда < запрос инструмента.
3. **Не писать файлы вне разрешённых папок** — инструмент обходит файловую
   политику DSH, значит проверять путь обязан сам.
4. **Возвращать модели текст, а не объект** — схема вывода `{ type: 'string' }`.
