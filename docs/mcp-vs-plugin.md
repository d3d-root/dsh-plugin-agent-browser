# Чем это отличается от MCP и что выбрать

В DSH есть два способа дать агенту браузер, и оба заканчиваются одним и тем же:
инструменты попадают в `ctx.tools`, а модель видит их как родные. Разница не в
интерфейсе инструментов, а в том, **где живёт браузер и кто им владеет**.

- **MCP-путь.** `@deepseek-ai/dsh-mcp-client` запускает внешний MCP-сервер
  (`@playwright/mcp`, `chrome-devtools-mcp`, облачный Browserbase) отдельным
  процессом и транслирует его инструменты в `ctx.tools` под именами
  `mcp__<serverName>__<tool>`. Браузер живёт вне DSH и не имеет доступа к
  интерфейсу приложения.
- **Этот плагин.** Держит настоящий `<webview>` в правой панели DSH и управляет
  им через собственный HTTP-мост. Браузер — часть приложения: тот же экземпляр,
  что видит пользователь.

Обе схемы рабочие. Ниже — что именно даёт каждая, где проходит граница и как
их совмещать, не наступив на грабли.

---

## 1. Как DSH подключает MCP-серверы

Источник: установленный пакет `@deepseek-ai/dsh-mcp-client` (`lib/types/*.d.ts`,
`README.md`, версия `0.2.1-rc.2`, MCP SDK `@modelcontextprotocol/client` 2.2.0).

### 1.1. Один плагин — один сервер

`dsh-mcp-client` — это namespace-плагин без default-экспорта: `apply(ctx,
config)` поднимает **одно** соединение с **одним** MCP-сервером и держит его до
выгрузки плагина. Несколько серверов = несколько записей в `cordis.yml` /
`cordis.patch.yml`. Никакой сервер не включён по умолчанию.

Жизненный цикл привязан к эффекту Cordis: выгрузка (в том числе HMR) закрывает
транспорт, снимает все инструменты и освобождает зарезервированное имя
`serverName`. Повторная загрузка с тем же `serverName` даёт те же публичные
имена инструментов — история сессии и правила разрешений не ломаются.

### 1.2. Поля конфига

| Поле | По умолчанию | Смысл |
|---|---|---|
| `transport` | обязательно | `stdio` или `streamable-http` |
| `serverName` | обязательно | Пространство имён инструментов; `[A-Za-z0-9_-]{1,32}`, уникально в пределах scope регистрации |
| `command` / `args` / `env` / `cwd` | `args: []`, `env: {}`, `cwd` — текущий | Только для `stdio`: исполняемый файл, аргументы (без shell-интерполяции), доп. переменные окружения, рабочий каталог |
| `url` / `headers` | — | Только для `streamable-http`: endpoint и дополнительные заголовки |
| `toolCallTimeoutMs` | `60000` | Таймаут на один `tools/call` или запрос ресурса |
| `maxInstructionBytes` | `32768` | Лимит UTF-8 байт на инструкции сервера; превышение отклоняет соединение |
| `failOnStartupError` | `false` | `true` — падение активации плагина, если первое соединение или синхронизация инструментов не удались |
| `reconnect.enabled` | `true` | Автопереподключение после потери соединения |
| `reconnect.initialDelayMs` / `maxDelayMs` / `maxAttempts` | `500` / `30000` / `10` | Экспоненциальный backoff; после 10 подряд неудач инструменты снимаются и переподключение прекращается до перезагрузки конфига |

Порядок старта: сначала плагин **ждёт** первое соединение и discovery, и только
потом активация завершается — то есть инструменты сервера уже есть в списке к
первому ходу модели. Если первое соединение упало, харнесс всё равно стартует,
инструментов этого сервера нет, в лог пишется ошибка. `failOnStartupError:
true` валит только активацию плагина; политика загрузки `app-boot` всё равно не
даёт опциональной MCP-записи уронить весь харнесс.

Пример записи:

```yaml
- id: mcp-browser
  name: "@deepseek-ai/dsh-mcp-client"
  config:
    transport: stdio
    serverName: browser
    command: "C:\\Program Files\\nodejs\\node.exe"
    args:
      - "...\\node_modules\\@playwright\\mcp\\cli.js"
      - --browser
      - chrome
      - --caps
      - vision,pdf
      - --output-dir
      - "...\\.dsh\\profiles\\desktop\\.playwright-mcp"
    cwd: "...\\.dsh\\profiles\\desktop"
    toolCallTimeoutMs: 120000
    failOnStartupError: false
```

### 1.3. Путь инструмента: сервер → `ctx.tools` → модель

1. SDK поднимает транспорт (`stdio` — дочерний процесс, `streamable-http` — URL).
2. Плагин ждёт discovery и строит **полное поколение** `ToolDefinition` для всех
   инструментов сервера.
3. Регистрация на `ctx.tools` идёт под именем `mcp__<serverName>__<rawName>`;
   при нормализации под контракт DeepSeek (64 символа, `[A-Za-z0-9_-]`)
   добавляется 12 hex-символов SHA-256, чтобы разные идентичности не склеились.
4. Смена списка инструментов на сервере → `notifications/tools/list_changed` →
   пере-синхронизация **атомарно**: неудачный fetch оставляет предыдущее
   поколение, конфликт регистрации откатывает всё новое поколение целиком.
5. Вызов: `tools/call` всегда получает **сырое** имя, публичное имя на провод не
   уходит. Результат приходит как обычный текст в порядке блоков; изображения
   проецируются в контекст как вложения; аудио и embedded-ресурсы —
   диагностическим текстом.

Два следствия, которые часто упускают:

- **Инструменты MCP стоят токенов всегда.** Описания и схемы входят в каждый
  запрос, пока инструменты зарегистрированы. Набор браузерного MCP — это
  два-три десятка инструментов с длинными описаниями, и они видны модели даже
  когда браузер не нужен.
- **Пересинхронизация ломает KV-кэш** от первого изменившегося токена схемы.
  Переподключение с тем же списком — не ломает.

### 1.4. Что MCP принципиально не умеет

Это ограничения пакета, а не «недоработки на будущее»:

- **Нет доступа к интерфейсу.** MCP-сервер — отдельный процесс, он не видит ни
  панелей DSH, ни состояния чата. Открыть вкладку в UI, показать пользователю
  страницу, попросить его что-то нажать — нельзя.
- **Нет MCP prompt-шаблонов и подписок на ресурсы.** Ресурсы читаются по
  требованию; инструкции сервера вставляются в системный промпт литеральным
  текстом.
- **Таймауты discovery/соединения — от SDK.** Своего таймаута у плагина нет:
  60 с по умолчанию на запросы SDK, плюс лимит страниц discovery.
- **Окружение дочернего процесса вычищается.** Для `stdio` переменные,
  совпадающие с `/KEY|PASSWORD|SECRET|TOKEN/i`, и все `DSH_*` выбрасываются;
  конфиг `env` мержится сверху. Практический вывод: ключи вида
  `BROWSERBASE_API_KEY`, `OPENAI_API_KEY` **надо задавать явно в `env`**.
- **Отмена кооперативная.** Внешний процесс не убивается мгновенно: инструмент,
  который игнорирует отмену, продолжает работать.

## 2. «Браузер по MCP»: что есть на рынке

### 2.1. `@playwright/mcp` (Microsoft)

Самый распространённый вариант. Работает по **accessibility-дереву**, а не по
пикселям: инструмент возвращает структурированный снимок страницы с `ref=e5`, и
модель кликает по ссылкам на элементы. Vision-модель не нужна.

- **Браузер:** свой, запускается сервером. `--browser chrome|firefox|webkit|msedge`,
  `--headless` (по умолчанию **headed**, окно видно), `--executable-path`.
- **Профили:** три режима — persistent (по умолчанию, каталог
  `ms-playwright/mcp-{channel}-{workspace-hash}`, **не** ваш повседневный Chrome),
  `--isolated` (профиль в памяти, состояние теряется при закрытии),
  `--extension` (подключение к уже открытым вкладкам вашего браузера).
- **Параллельность:** один persistent-профиль нельзя открыть дважды —
  «concurrent MCP clients sharing the same workspace will conflict»; для
  параллельных клиентов нужен `--isolated` или свой `--user-data-dir` на
  каждого. Внутри одной сессии `browser_tabs` умеет создавать вкладку в
  именованном изолированном контексте (`isolatedContext`).
- **Возможности:** навигация, клики, ввод, клавиши, drag&drop, диалоги, вкладки,
  снимки, сеть и мокинг (`--caps=network`), storage state (`--caps=storage`),
  PDF (`--caps=pdf`), DevTools/трейсинг/видео (`--caps=devtools`), координатные
  инструменты мыши (`--caps=vision`), плюс `browser_run_code_unsafe` в базовом
  наборе — по собственному описанию «RCE-эквивалент».
- **Токены:** снимки большие. Каталог `.playwright-mcp` содержит `page-*.yml`
  размером **20–240 КБ** на один снимок — это десятки тысяч токенов на страницу.

### 2.2. `chrome-devtools-mcp` (Google)

Управляет **живым Chrome** через Puppeteer/CDP и, в отличие от Playwright MCP,
продаёт не автоматизацию, а **инспекцию**: трассировки производительности,
network, консоль с source maps, память, WebAuthn, эмуляция, скриншоты.

- **Браузер:** стабильный Chrome, `--headless` (по умолчанию **headed**),
  `--channel canary|dev|beta|stable`, `--executablePath`.
- **Профиль:** `%USERPROFILE%\.cache\chrome-devtools-mcp\chrome-profile` —
  отдельный от повседневного Chrome; **один браузер на каталог**, для
  параллельных инстансов — `--isolated`. `--autoConnect` (Chrome 144+)
  подключается к **вашему** запущенному Chrome.
- **Параллельность:** `--pageIdRouting` (по умолчанию включён) добавляет
  `pageId` в page-scoped инструменты, чтобы несколько сессий не отбирали вкладки
  друг у друга.
- **Особенности:** по умолчанию собирает usage statistics в Google
  (`--no-usage-statistics`), есть `--blockedUrlPattern` / `--allowedUrlPattern`,
  `--slim`, `--experimentalVision`.

### 2.3. `@modelcontextprotocol/server-puppeteer`

Исторический референсный сервер. **Архивирован и не поддерживается**: npm-пакет
помечен deprecated с отсылкой на
[servers-archived](https://github.com/modelcontextprotocol/servers-archived).
Умеет ровно базовое: navigate, screenshot, click, hover, fill, select, evaluate.
Launch options передаются аргументом инструмента (`launchOptions`,
`allowDangerous`) — то есть **модель может перезапустить браузер с другими
флагами**, включая потенциально опасные.

Для нового проекта не выбирать: нет поддержки, нет изоляции профилей, нет
параллельных контекстов, нет vision/координат, протокол старый.

### 2.4. Browserbase MCP

Облачные браузеры. Self-hosted репозиторий `mcp-server-browserbase`
**архивирован**, рекомендуется hosted-сервер `https://mcp.browserbase.com/mcp`
(Streamable HTTP) или npm `@browserbasehq/mcp` локально. Шесть инструментов:
`start` / `end` / `navigate` / `act` / `observe` / `extract` — то есть не «клик
по ref», а **действие на естественном языке**, которое исполняет Stagehand со
своей LLM.

- **Браузер:** в облаке, на вашей машине ничего не запускается. Нужны
  `BROWSERBASE_API_KEY` и `BROWSERBASE_PROJECT_ID`.
- **Видимость:** по умолчанию пользователь ничего не видит; «окно» — это Live
  View URL, который можно вставить в `<iframe>`/`<webview>` и даже сделать
  read/write, то есть пустить человека в цикл.
- **Параллельность:** сильная сторона — каждая сессия это отдельный удалённый
  браузер; лимиты по тарифу.
- **Цена:** платно, плюс второй LLM внутри, плюс данные уходят наружу.

### 2.5. Browser Use MCP

`uvx --from 'browser-use[cli]' browser-use --mcp` — локальный stdio-сервер на
Python. Даёт низкоуровневые инструменты и `retry_with_browser_use_agent` —
«прогони задачу целиком своим агентом, если прямое управление не вышло».

- **Браузер:** локальный, по умолчанию headless (`BROWSER_USE_HEADLESS=false`,
  чтобы показать окно).
- **Параллельность:** есть управление сессиями — `browser_list_sessions`,
  `browser_close_session`, `browser_close_all`.
- **Зависимости:** Python + `uv`/`uvx`, свой LLM-ключ.
- **Особенность:** `BROWSER_USE_DISABLE_SECURITY=true` отключает защитные
  механизмы браузера — включать только осознанно.

### 2.6. Сводка «что умеет»

| | Playwright MCP | chrome-devtools-mcp | server-puppeteer | Browserbase MCP | Browser Use MCP |
|---|---|---|---|---|---|
| Состояние | активно | активно | **архив** | hosted / self-hosted архив | активно |
| Внешний браузер | свой или ваш через `--extension` | свой Chrome или ваш через `--autoConnect` | свой | облако | свой |
| Окно видит пользователь | да (headed по умолчанию) | да (headed по умолчанию) | да / нет (docker) | нет (Live View по запросу) | нет по умолчанию |
| Параллельные сессии | по серверу на клиента / `isolatedContext` | `pageIdRouting` / `--isolated` | нет | да (сессии) | да (сессии) |
| Изоляция профилей | persistent / `--isolated` / `--storage-state` | общий каталог / `--isolated` | нет | contextId | сессии |
| Ввод как у человека | CDP-события; координаты через `--caps=vision` | CDP-события; координаты через `--experimentalVision` | CDP | CDP в облаке | CDP |
| Зависимости | Node 18+, браузер Playwright | Node LTS, Chrome | Node, Chromium | ключ + сеть | Python, uv, LLM-ключ |
| Токен-цена | высокая (a11y-снимки) | высокая (снимки/трассы) | низкая, но возможностей мало | средняя | средняя |

## 3. Честное сравнение по осям

### 3.1. Видимость для пользователя

| Схема | Что видит человек | Может ли вмешаться |
|---|---|---|
| Playwright MCP, headed | отдельное окно Chrome, живой браузер | да, физически |
| chrome-devtools-mcp, headed | отдельное окно Chrome | да |
| любой MCP + `--headless` | ничего | нет |
| Browserbase | ничего, пока не открыть Live View | да, если Live View в режиме read/write |
| Этот плагин (`<webview>`) | панель внутри DSH, рядом с чатом | да, и это тот же самый экземпляр |

Ключевая разница: MCP-браузер — **отдельное окно**, которое живёт по своим
правилам (headed/headless, свой профиль, свой idle-timeout). Плагин — **часть
интерфейса**: пользователь и агент смотрят на один и тот же документ, и «покажи,
что ты делаешь» не требует объяснений. Это же и главный риск: пользователь
может мышью увести страницу из-под агента посреди сценария.

### 3.2. Параллельность нескольких агентов

- **MCP.** Один `stdio`-инстанс = одно соединение = один браузер. Все агенты в
  одном scope делят его: инструменты одни и те же, вкладки одни и те же,
  «текущая вкладка» — глобальное состояние. Playwright MCP разрешает
  параллельность только через отдельные инстансы (`--isolated`/свой
  `--user-data-dir`) или через `isolatedContext` внутри одного;
  chrome-devtools-mcp — через `pageIdRouting` и `--isolated`. Ни то, ни другое
  не даёт «каждому агенту свой браузер» бесплатно.
- **Этот плагин.** Каждый инструмент получает `exec.agent.id` — сессию своего
  агента — и передаёт её мосту. Мост выбирает панель **этой** сессии, поэтому
  два агента в разных чатах работают одновременно и не перехватывают команды
  друг друга. Внутри одного чата с несколькими вкладками команды идут в
  видимую; конкретную панель можно назвать явно.

Вывод: плагин даёт параллельность **по сессиям из коробки**, а внутри сессии —
по явной адресации. MCP требует отдельных инстансов или контекстов.

### 3.3. Изоляция cookie и профилей

- Playwright MCP: persistent-профиль привязан к хешу рабочего каталога клиента →
  разные проекты автоматически получают разные профили; `--isolated` даёт
  чистое состояние на сессию; `--storage-state` переносит cookies точечно.
  **Важно:** это не ваш повседневный Chrome.
- chrome-devtools-mcp: один каталог профиля на канал; `--isolated` — временный;
  `--autoConnect` — **ваш** профиль целиком.
- Browserbase: `contextId` + `--persist` — лучшая изоляция, потому что браузер
  вообще не на вашей машине.
- **Этот плагин:** ключ аренды `<webview>` — строка workspace, и один и тот же
  ключ даёт общий профиль Chromium. Плагин берёт ключ
  `dsh-agent-browser:<id сессии>`, поэтому **каждый чат получает свой профиль**:
  свои cookie, свои логины, никакого пересечения с другими чатами и с вашим
  повседневным Chrome. Цена: после перезапуска DSH профили живут в памяти
  процесса и логины теряются — это осознанный компромисс в пользу изоляции.

### 3.4. Нативные события ввода (капчи)

- MCP на Playwright/Puppeteer: клики и ввод идут через протокол автоматизации
  (CDP для Chromium), то есть это **доверенные** события браузера
  (`isTrusted: true`), а не `element.click()` из JS. Для капч этого достаточно
  на уровне «событие принято», но недостаточно на уровне «похоже на человека»:
  нет траектории движения мыши, нет пауз. Координатные инструменты
  (`--caps=vision` у Playwright, `--experimentalVision` у chrome-devtools) дают
  `mouse_click_xy` / `mouse_drag_xy` — это уже пригодно для слайдер-пазлов.
- **Этот плагин:** `webview.sendInputEvent()` — тоже настоящие события Chromium,
  плюс `browser_drag` с человеческой траекторией (плавность, дрожание, паузы),
  плюс `browser_mouse_click` отдельно от синтетического `browser_click_at` —
  ровно потому, что часть капч различает доверенные и синтетические клики.
- **Честно:** ни одна схема не «решает капчу». Разница в том, что в плагине
  человек может просто подойти и дорешать её в том же окне, а в headless-MCP —
  нет. Это не техническая, а процессная разница, и она важнее любых флагов.

### 3.5. Установка и зависимости

| | Что нужно поставить |
|---|---|
| Playwright MCP | Node 18+; при первом запуске — браузеры Playwright, если не использовать системный Chrome |
| chrome-devtools-mcp | Node LTS + установленный Chrome |
| server-puppeteer | Node + Chromium (или Docker) |
| Browserbase | ничего локально, но ключ, аккаунт, сеть и деньги |
| Browser Use | Python, `uv`, LLM-ключ |
| **Этот плагин** | ничего: Electron уже несёт Chromium, Node внутри DSH уже есть |

Сильный аргумент в пользу плагина для десктопного продукта: **ноль внешних
зависимостей и ноль установки**. MCP-вариант всегда требует «а у пользователя
есть Node? а Chrome? а версия?».

### 3.6. Надёжность и сопровождение

- **MCP** даёт готовое: переподключение с backoff, атомарную замену поколений
  инструментов, стабильные имена, диагностику. Но появляется вторая точка
  отказа — дочерний процесс, который может не стартовать, упасть, зависнуть на
  discovery, и тогда «инструментов просто нет».
- **Этот плагин** — вы владеете всем: мост, гонки, таймауты, HMR, жизненный
  цикл. Зато и отладка полностью ваша: журнал моста, `/health`, `/state`.
- Практика: у MCP-браузеров ломается версия (Playwright MCP 0.0.x меняет флаги
  и имена инструментов между релизами), у плагинов — состояние после горячей
  перезагрузки (мост переживает перезагрузку модуля, инструменты регистрируются
  заново).

### 3.7. Безопасность: что видит агент

- **MCP-браузер видит всё, что видит браузер.** Playwright MCP с
  persistent-профилем — все cookie и storage этого профиля; chrome-devtools-mcp
  с `--autoConnect` — **все окна вашего профиля**; Browserbase — всё, что в
  облачной сессии, плюс трафик уходит вендору.
- **Отдельный риск — контент страницы как недоверенный ввод.** Любой текст на
  странице может содержать инструкции для модели. Playwright MCP прямо
  предупреждает: имена, описания, схемы и результаты таких инструментов —
  untrusted input.
- **`browser_run_code_unsafe`** (Playwright MCP) и `puppeteer_evaluate` — это
  выполнение произвольного JS в процессе сервера, то есть RCE-эквивалент. У
  Playwright MCP он лежит в базовом наборе, а не за отдельным флагом.
- **Этот плагин** видит ровно одну панель и её `partition`: нет доступа к
  личным cookie пользователя, нет доступа к другим вкладкам DSH. Мост закрыт
  токеном и loopback-проверкой, тело запроса ограничено 8 МБ, запись
  скриншотов — только в разрешённые папки. Подробности — в
  [безопасности README](../README.md#безопасность).

## 4. Что выбрать

### 4.1. Когда хватает MCP

- Браузер нужен **пакетно**, а не интерактивно: собрать данные, снять PDF,
  прогнать сценарий, проверить вёрстку.
- Не важно, что пользователь не видит окно (headless) — или окно даже мешает.
- Нужны вещи, которых в плагине нет: трассировка производительности,
  network-мокинг, память, WebAuthn, a11y-снимки, полный DevTools.
- Не нужны сессии пользователя и капчи; либо наоборот — нужны **именно** сессии,
  и тогда `--extension` / `--autoConnect`.
- Команда — один агент, один браузер.
- Готовы тянуть Node + Chrome + обновления `@playwright/mcp`.

### 4.2. Когда нужен этот плагин

- Человек должен **видеть** и **вмешаться**: капча, 2FA, «введи пароль сам»,
  «покажи, куда ты нажал».
- Браузер — часть продукта, а не инструмент разработчика.
- Нужен контроль над отпечатком (`User-Agent`, правки `outerWidth`).
- Нельзя требовать от пользователя установки Node/Chrome.
- Нужен доступ к интерфейсу (открыть вкладку, вывести на экран, переключить чат).
- Нужны разные профили у разных чатов.

### 4.3. Гибриды

**A. Плагин как UI + MCP как движок (через CDP).** Запустить отдельный Chromium
с `--remote-debugging-port` и подключить `@playwright/mcp --cdp-endpoint`.
**Но:** порт отладки Electron открывает управление **всем приложением**,
включая рендерер с чатом и токенами. Это эскалация привилегий из «агент умеет
браузер» в «агент умеет DSH». Если делать — только отдельный Chromium-процесс,
не окно приложения, и на loopback с аутентификацией.

**B. MCP как движок + плагин как окно.** Для облака это штатно: Browserbase
отдаёт Live View URL на каждую вкладку, его можно вставить в `<webview>` и
получить «окно в облачный браузер» с возможностью вмешаться. Задержка, платно,
данные уходят вендору.

**C. Плагин сам выставляет MCP-сервер.** Мост уже HTTP с JSON-командами —
обернуть его в Streamable HTTP MCP-сервер и подключить к DSH через тот же
`dsh-mcp-client` (или отдать внешним клиентам: Claude Code, Cursor). Плюсы:
инструменты переносимы, один код на все клиенты, бесплатно достаётся
переподключение. Минусы: два транспорта вместо одного, дублирование таймаутов,
и всё равно нужен плагин для UI.

**D. Два движка сразу, с явным разделением.** Плагин — основной для
интерактивных задач, MCP — для того, чего плагин не умеет. Работает только при
жёстком правиле «какой браузер сейчас главный»: разные имена (`browser_*`
против `mcp__browser__browser_*`), разные профили, и в инструкции агенту явно
написано, когда какой использовать.

**Рекомендация:** держать включённым **один** браузерный стек на профиль. Для
десктопного сценария с человеком в цикле — плагин; MCP включать точечно, под
конкретную задачу и с отдельным `serverName`. Схема C — самый чистый способ
переиспользовать плагин снаружи.

### 4.4. Архитектурные ловушки

1. **Два источника правды.** Пользователь смотрит в панель, а агент ходит в
   headless-MCP (или наоборот). Симптом: «у меня не работает», «я не это вижу».
   Лечится только одним активным браузером на профиль.
2. **MCP-инструмент не может показать себя.** Из MCP нельзя открыть панель,
   вывести вкладку на экран, попросить пользователя нажать.
3. **Таймауты двух уровней.** Снаружи `toolCallTimeoutMs`, внутри — свои
   таймауты сервера. Ожидание капчи/2FA легко выбивает наружный лимит. Политика
   `dsh-tool-call-timeout-policy` **кооперативная**: просит инструмент
   остановиться, но не убивает внешний процесс.
4. **Вычищенное окружение.** `stdio`-сервер получает окружение без переменных с
   `KEY|PASSWORD|SECRET|TOKEN`. Ключи задавать **только** через `env` в конфиге.
5. **Профиль ≠ ваш браузер.** Persistent-профиль Playwright —
   `ms-playwright/mcp-{channel}-{hash}`, chrome-devtools —
   `~/.cache/chrome-devtools-mcp/chrome-profile`. Ожидание «там мои логины»
   неверно; и один профиль нельзя открыть дважды.
6. **Коллизия имён и путаница модели.** Оставить оба набора включёнными —
   получить `browser_navigate` и `mcp__browser__browser_navigate` с одинаковым
   смыслом и разным состоянием. Модель будет выбирать случайно.
7. **Мост на loopback без аутентификации.** `127.0.0.1:<порт>` плюс
   `access-control-allow-origin: *` означает: любой локальный процесс и любая
   страница могут отправлять команды. Нужен токен, loopback-проверка и предел
   тела запроса — в этом плагине так и сделано.
8. **HMR и двойной `listen`.** Мост переживает перезагрузку модуля, а `apply()`
   вызывается заново — отсюда проверка «мост уже поднят», состояние в
   `globalThis` и повторные попытки занять порт.
9. **Гонка «текущей вкладки».** Несколько панелей + неявный выбор вкладки =
   `navigate` в одну, `read` в другую. Лечится адресацией по сессии и
   закреплением панели.
10. **Стелс — это не одна правка.** В Electron-webview `navigator.webdriver`
    обычно `false`, но `outerWidth/outerHeight === 0` выдаёт встроенный браузер;
    правки отпечатка нужно применять на **каждой** новой странице (`dom-ready`),
    а не один раз при создании webview.
11. **Скриншоты и приватность.** `browser_screenshot` кладёт PNG на диск и отдаёт
    путь модели; в кадр попадает всё, что на экране. Для MCP то же самое:
    `--output-dir`/`--output-max-size` стоит ограничить.
12. **`browser_run_code_unsafe` — в базовом наборе.** Если такой возможности не
    нужно — держать браузерный MCP в отдельном инстансе с узким набором
    инструментов.

## 5. Чек-лист выбора

- Нужен человек в цикле или видимое окно → **плагин**.
- Нужны капчи и живой профиль, куда человек может вмешаться → **плагин**; если
  браузер облачный — Browserbase + Live View.
- Нужны трассировки, network, PDF, a11y-снимки → **MCP**.
- Нужна параллельность многих агентов → **плагин** (по сессиям из коробки) или
  MCP с отдельными инстансами.
- Нельзя требовать установки Node/Chrome → **плагин**.
- Нужно отдать браузер наружу → обернуть мост плагина в MCP-сервер.
- Сомневаетесь → начните с плагина и включайте MCP точечно, под задачу.
