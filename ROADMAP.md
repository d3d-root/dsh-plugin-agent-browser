# План развития

Состояние на 2.1.1: 35 инструментов, ~4600 строк, 79 тестов, публикация в
npm через OIDC. Ниже — что делать дальше, по убыванию пользы на единицу работы.

Легенда сложности: **S** — до вечера, **M** — выходные, **L** — неделя.

---

## Уровень 1: то, что реально мешает работать

Это дыры, в которые пользователь упирается в первый же день.

### 1.1. Cookie и логины не выживают перезапуск ⭐ главное

Сейчас профиль Chromium живёт в памяти процесса: перезапустил DSH — заново
логинься на всех сайтах. Для сценариев «агент ходит в личный кабинет» это
блокер.

**Что делать:** выяснить, принимает ли `window.dshDesktop.browser.acquire()`
флаг постоянного профиля (`persist:`-префикс у partition в Electron). Если да —
включить его, ключом сделать id сессии. Если нет — просить в DSH API, а пока
предложить настройку `profileKey`, чтобы профили были хотя бы общими между
чатами по желанию.

Сложность: **S–M** (зависит от того, что умеет API DSH).

### 1.2. Загрузка файлов на сайт

Нельзя прикрепить резюме, отправить картинку в форму, залить CSV. Это первое,
чего не хватает в реальных задачах.

**Что делать:** инструмент `browser_upload { selector, files }`. В Electron это
`webContents.debugger` + `DOM.setFileInputFiles`, либо `webview`-событие
`will-attach-webview`. Нужна проверка, что пути ограничены рабочим каталогом
чата — иначе агент сможет отправить на сайт любой файл с диска.

Сложность: **M**.

### 1.3. Скачивание файлов

Обратная задача: нажал «Скачать» — файл ушёл в системную папку загрузок, агент
его не видит.

**Что делать:** перехватить `will-download`, сохранять в каталог чата, вернуть
путь. Плюс `browser_downloads` — список скачанного.

Сложность: **M**.

### 1.4. Полностраничный скриншот

Сейчас только видимая область. Для «покажи всю страницу» и для сравнения
вёрстки нужен весь документ.

**Что делать:** `browser_screenshot { fullPage: true }` через
`debugger`/`Page.captureScreenshot` с `captureBeyondViewport`, либо склейка
скроллом (грубее, но без CDP).

Сложность: **S–M**.

### 1.5. Ожидание «сеть успокоилась»

`browser_wait` умеет ждать селектор или текст, но не «дождись, пока догрузятся
данные». Из-за этого `browser_read` иногда читает пустой скелет страницы.

**Что делать:** слушать `did-start-loading`/`did-stop-loading` и сетевые события
`webview`, добавить `waitUntil: 'networkidle'` в `browser_navigate`.

Сложность: **S**.

## Уровень 2: чтобы агент работал точнее

### 2.1. Элементы с индексами вместо клика по тексту

Сейчас `browser_click` ищет по видимому тексту. На странице с тремя «Купить»
это лотерея.

**Что делать:** `browser_find { selector | text }` возвращает нумерованный
список найденного (текст, координаты, видимость), затем `browser_click { index }`.
Агенту проще: сначала посмотрел, потом нажал точно.

Сложность: **M**.

### 2.2. Структурированное извлечение

`browser_read` отдаёт простыню текста. Для таблиц, списков, карточек нужен JSON.

**Что делать:** `browser_extract { selector, fields }` — вытащить массив
объектов по CSS-селекторам. Это превращает парсинг Авито из «прочитать 3000
символов» в готовый массив.

Сложность: **M**.

### 2.3. Несколько вкладок в одном чате

Сейчас `multiple: true` в регистрации есть, но команды идут в видимую вкладку —
при двух вкладках поведение непредсказуемо.

**Что делать:** адресация по `tabId` во всех инструментах (необязательный
параметр), `browser_tabs` показывает id, `browser_open { tabId }` создаёт
именованную.

Сложность: **M**.

### 2.4. Мелочи, которые часто нужны

- `browser_zoom` — масштаб (мелкий сайт не влезает в узкую панель);
- `browser_find_in_page` — поиск по тексту страницы;
- `browser_history` — куда ходили в этом чате;
- `browser_pdf` — сохранить страницу в PDF.

Сложность: **S** каждая.

## Уровень 3: сильные стороны и отличия

### 3.1. Блокировка рекламы и трекеров

Даёт три выгоды сразу: страницы грузятся быстрее, агент меньше ждёт, капчи
появляются реже (меньше подозрительной активности).

**Что делать:** `webRequest.onBeforeRequest` в сессии профиля + список
хостов-трекеров. Настройка `blockAds: true`.

Сложность: **M**.

### 3.2. Прокси

Для сайтов, которые блокируют по гео, и для разделения «личное/рабочее» по
чатам. Настройка `proxy` на профиль.

Сложность: **M**.

### 3.3. Трассировка для отладки

Когда у пользователя «не работает», нужен не журнал из строк, а запись: какие
команды, какие ответы, скриншоты до и после.

**Что делать:** `debug: 'trace'` — писать JSONL с командами и ответами в
каталог чата.

Сложность: **M**.

### 3.4. Устойчивость к капчам

Уже есть настоящие события мыши и человеческая траектория. Дальше:

- задержки при вводе текста (сейчас вставка мгновенная);
- согласованность отпечатка (UA, `navigator.platform`, `outerWidth` — сейчас
  `outerWidth` нулевой, это заметный признак автоматизации);
- `browser_set_ua` уже есть, но отпечаток за ним не меняется.

Сложность: **M**.

англоязычный пользователь не поймёт, что ответил агент, а в README на GitHub
это выглядит как региональный проект.

**Что делать:** вынести описания инструментов в словарь, добавить `en` как
основной для описаний, `ru` оставить для сообщений пользователю.

Сложность: **M**.

### 4.2. CI на каждый коммит

Сейчас Actions запускаются только по тегу. Добавить второй workflow: тесты и
`node --check` на push и pull request.

Сложность: **S**.

именно там ломались все баги этой разработки.

**Что делать:** выделить из `client.js` чистые функции (разбор URL, поиск
элемента по тексту, траектория перетаскивания) в модуль и покрыть их.

Сложность: **M**.

### 4.4. Разбить `client.js`

капча-хелперы.

Сложность: **S–M** (механическая работа, но нужен аккуратный перенос).

## Чего делать не стоит

- **Не тащить Playwright.** Сейчас плагин ничего не требует — Chromium уже в
  DSH. Playwright добавит сотни мегабайт и вторую модель управления браузером.
- **Не делать «универсальный парсер сайтов».** `browser_extract` + `eval`
  покрывают это гибче.
- **Не гнаться за числом инструментов.** 22 — уже много; лучше сделать
  существующие надёжнее.
